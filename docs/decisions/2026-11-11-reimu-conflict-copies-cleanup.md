# 2026-11-11 · 清理两个仓库里的同步冲突副本

两个仓库都在 `~/Documents` 下，这个目录被文件同步服务接管（副本文件带 `dataless` 标记，内容只在云端）。
资源包用「整个目录删掉再重写」的方式重新导出时，同步服务留下了 `名字 2.png`、`名字 3.md` 这样的冲突副本。
我此前只报告、没有动；用户回复「可以处理一下冲突副本」。

## 盘点

按文件名规则（`原名 数字.扩展名`）找到 589 个文件和 8 个空目录，没有一个被 Git 跟踪。

| | Consumer `gensokyo-codex-pets` | Harness `build/`（Git 忽略） |
| --- | --- | --- |
| 与原件内容逐字节相同 | 152 | 340 |
| 与原件内容不同 | 5（五个包的旧版 `README`） | 88（重新导出之前的旧帧、旧报告，修改时间都不晚于原件） |
| 空的编号目录（`frames 2` 等，原目录存在） | 5 | 3 |
| 没有对应原件 | 0 | 4 |

## 处理

有原件的 585 个文件和 8 个空目录**移到废纸篓** `~/.Trash/reimu-conflict-copies-20261111/`（保留原来的相对路径），没有永久删除。
移动时系统先把云端内容取回，所以废纸篓里的是完整文件（共 243.7 MB），内容比对是在移动之后对着原件做的。
清单 `build/reimu-conflict-copies-cleanup-20261111/moved.tsv`：状态、副本路径、原件路径、两边大小、内容是否相同。还原方法是把文件从废纸篓移回清单里的路径。

没有动的 4 个：`build/m3-install-recovery/sprite_animation_harness-0.4.0.dist-info/` 下的 `RECORD 2`、`REQUESTED 2`、`direct_url 2.json`、
`entry_points 2.txt`。它们没有不带编号的原件，是 9 月那次安装恢复留下的快照，不能当作副本处理。

## 核对

清理后两个仓库的 `git status` 只剩本次有意的改动，Consumer 仓库门禁通过，已跟踪文件没有变化。

## 边界

- 原因没有消除：只要仓库还在被同步的 `~/Documents` 里、导出脚本还是先删目录再重写，副本还会再出现。提交时继续只按文件名添加，不用 `git add -A`。
- 是哪一个同步服务、为什么产生冲突，我没有核实，只看到了文件上的 `dataless` 标记。
- 清空废纸篓之后这些副本无法从本机恢复；内容不同的 93 个是旧版本，原件都还在。
